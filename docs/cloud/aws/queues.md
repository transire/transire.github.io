# AWS Queue Integration (SQS)

## Overview

Transire deploys queue handlers to AWS Lambda with SQS (Simple Queue Service) event sources. This provides:

- **Asynchronous processing** - Decouple HTTP requests from long-running work
- **Automatic retries** - Failed messages retry with exponential backoff
- **Dead Letter Queues (DLQ)** - Capture persistently failing messages
- **Batch processing** - Process up to 10 messages per Lambda invocation
- **Type safety** - Prevent wrong-type messages with runtime validation

The same queue handler code runs identically in local mode and AWS Lambda.

## Architecture

```
Producer (HTTP handler)
    ↓
Enqueue message
    ↓
SQS Queue
    ↓
Lambda Event Source Mapping
    ↓
Lambda Function (Queue Handler)
    ↓
Process batch of messages
    ↓
Partial batch failure → retry failed messages
    ↓
Persistent failures → DLQ
```

### Key Components

| Component | Purpose | Configuration |
|-----------|---------|---------------|
| **SQS Queue** | Message storage | Generated by Transire |
| **Lambda Function** | Runs your handler | One per queue handler |
| **Event Source Mapping** | Polls SQS, invokes Lambda | Auto-configured |
| **DLQ** | Failed messages | Auto-generated |
| **IAM Role** | Permissions | Auto-generated |

## Message Flow

### 1. Producer Enqueues Message

From an HTTP handler or another queue handler:

```go
import "github.com/transire/sdk-go/queue"

type ProcessOrder struct {
    OrderID   string  `json:"order_id"`
    Total     float64 `json:"total"`
    UserID    string  `json:"user_id"`
    Timestamp int64   `json:"timestamp"`
}

func createOrder(w http.ResponseWriter, r *http.Request) {
    // Create order in database...
    order := &ProcessOrder{
        OrderID:   "order_123",
        Total:     99.99,
        UserID:    "user_456",
        Timestamp: time.Now().Unix(),
    }

    // Enqueue for async processing
    err := queue.Enqueue(r.Context(), "process-orders", order)
    if err != nil {
        http.Error(w, "Failed to enqueue", http.StatusInternalServerError)
        return
    }

    // Return immediately to client
    w.WriteHeader(http.StatusAccepted)
    json.NewEncoder(w).Encode(map[string]string{
        "status":   "accepted",
        "order_id": order.OrderID,
    })
}
```

### 2. Message Sent to SQS

Transire's queue producer:

1. Serializes message to JSON
2. Adds `__type` field for type safety
3. Sends to SQS queue

**SQS Message:**
```json
{
  "MessageId": "abc123",
  "Body": "{\"__type\":\"github.com/acme/orders.ProcessOrder\",\"order_id\":\"order_123\",\"total\":99.99,\"user_id\":\"user_456\",\"timestamp\":1698765432}"
}
```

### 3. Lambda Polls SQS

Event Source Mapping polls SQS and invokes Lambda with a batch:

```json
{
  "Records": [
    {
      "messageId": "abc123",
      "body": "{\"__type\":\"github.com/acme/orders.ProcessOrder\",...}",
      "attributes": {
        "ApproximateReceiveCount": "1",
        "SentTimestamp": "1698765432000"
      }
    },
    {
      "messageId": "def456",
      "body": "{\"__type\":\"github.com/acme/orders.ProcessOrder\",...}",
      "attributes": {
        "ApproximateReceiveCount": "1",
        "SentTimestamp": "1698765433000"
      }
    }
  ]
}
```

### 4. Your Handler Processes Batch

```go
import "github.com/transire/sdk-go"

func processOrders(ctx context.Context, msgs []ProcessOrder) error {
    br := transire.NewBatchResult(len(msgs))

    for i, order := range msgs {
        // Process each order
        if err := chargePayment(ctx, order); err != nil {
            log.Printf("Failed to charge order %s: %v", order.OrderID, err)
            br.Fail(i, err)
            continue
        }

        if err := sendConfirmation(ctx, order); err != nil {
            log.Printf("Failed to send confirmation for %s: %v", order.OrderID, err)
            br.Fail(i, err)
            continue
        }

        log.Printf("Successfully processed order %s", order.OrderID)
    }

    // Return partial batch failure response
    return br.Error()
}
```

### 5. Failed Messages Retry

If `br.Fail(i, err)` is called, that message:

1. Returns to SQS queue (visibility timeout expires)
2. Retries with exponential backoff
3. After max retries → moved to DLQ

## Deployment

### Generated Resources

When you run `transire deploy`, these AWS resources are created:

#### SQS Queue
```hcl
resource "aws_sqs_queue" "process_orders" {
  name                      = "${var.service_name}-process-orders"
  visibility_timeout_seconds = 180  # 3× Lambda timeout
  message_retention_seconds  = 345600  # 4 days
  receive_wait_time_seconds = 10  # Long polling

  # From transire.yaml queues config
  max_receive_count = 3

  # Dead Letter Queue
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.process_orders_dlq.arn
    maxReceiveCount     = 3
  })

  # Enable server-side encryption
  sqs_managed_sse_enabled = true
}
```

#### Dead Letter Queue
```hcl
resource "aws_sqs_queue" "process_orders_dlq" {
  name                      = "${var.service_name}-process-orders-dlq"
  message_retention_seconds = 1209600  # 14 days
  sqs_managed_sse_enabled  = true
}
```

#### Lambda Function
```hcl
resource "aws_lambda_function" "process_orders" {
  function_name = "${var.service_name}-process-orders"
  role         = aws_iam_role.lambda_exec.arn

  runtime       = "provided.al2023"
  architectures = ["arm64"]
  memory_size   = 512
  timeout       = 60

  # Handler selection
  environment {
    variables = {
      TRANSIRE_HANDLER = "queue:process-orders"
    }
  }

  filename         = "dist/queue-handler.zip"
  source_code_hash = filebase64sha256("dist/queue-handler.zip")
}
```

#### Event Source Mapping
```hcl
resource "aws_lambda_event_source_mapping" "process_orders" {
  event_source_arn = aws_sqs_queue.process_orders.arn
  function_name    = aws_lambda_function.process_orders.arn

  # From transire.yaml queues config
  batch_size                         = 10
  maximum_batching_window_in_seconds = 5

  # Partial batch failure support
  function_response_types = ["ReportBatchItemFailures"]

  # Scaling config
  scaling_config {
    maximum_concurrency = 10
  }
}
```

### Configuration

Control queue behavior via `transire.yaml`:

```yaml
queues:
  process-orders:
    batch_size: 10              # Messages per Lambda invocation (1-10)
    visibility_timeout: 180     # Seconds (auto-set to 3× timeout)
    max_retries: 3              # Attempts before DLQ
    max_concurrency: 10         # Max parallel Lambda invocations
    batching_window: 5          # Seconds to wait for full batch

  send-emails:
    batch_size: 1               # Process one at a time
    max_retries: 5              # More retries for transient failures
```

## Type Safety

### Type Field

Every message includes `__type` field:

```json
{
  "__type": "github.com/acme/orders.ProcessOrder",
  "order_id": "order_123",
  "total": 99.99
}
```

### Runtime Validation

On consume, Transire validates:

1. `__type` field exists
2. Type matches handler signature: `func(ctx, []ProcessOrder) error`
3. JSON unmarshals to type

**Type mismatch → DLQ** (prevents poison pill messages)

### Schema Evolution

Safe changes:

```go
// ✅ Add optional field (with default)
type ProcessOrder struct {
    OrderID   string  `json:"order_id"`
    Total     float64 `json:"total"`
    UserID    string  `json:"user_id"`
    Priority  string  `json:"priority,omitempty"`  // NEW: optional
}

// ✅ Add field with json default
type ProcessOrder struct {
    OrderID   string  `json:"order_id"`
    Total     float64 `json:"total"`
    UserID    string  `json:"user_id"`
    Source    string  `json:"source"`  // NEW: will be empty string for old messages
}
```

Breaking changes (require DLQ drain):

```go
// ❌ Remove required field
type ProcessOrder struct {
    OrderID string  `json:"order_id"`
    // Total   float64 `json:"total"`  // REMOVED: breaks old messages
}

// ❌ Change field type
type ProcessOrder struct {
    OrderID string `json:"order_id"`
    Total   int    `json:"total"`  // Was float64: breaks unmarshaling
}
```

## Batch Processing

### Batch Result

Track success/failure per message:

```go
func processOrders(ctx context.Context, msgs []ProcessOrder) error {
    br := transire.NewBatchResult(len(msgs))

    for i, order := range msgs {
        if err := process(ctx, order); err != nil {
            // Mark this message as failed
            br.Fail(i, err)
            continue
        }
        // Success is implicit (don't call br.Success)
    }

    // Returns partial batch failure response
    // Failed messages return to queue for retry
    return br.Error()
}
```

### Concurrency Within Batch

Process messages in parallel:

```go
func processOrders(ctx context.Context, msgs []ProcessOrder) error {
    br := transire.NewBatchResult(len(msgs))

    var wg sync.WaitGroup
    for i, order := range msgs {
        wg.Add(1)
        go func(idx int, ord ProcessOrder) {
            defer wg.Done()

            if err := process(ctx, ord); err != nil {
                br.Fail(idx, err)
            }
        }(i, order)
    }

    wg.Wait()
    return br.Error()
}
```

**Warning:** Watch for race conditions and context cancellation.

### Ordering Guarantees

**Standard Queue:**
- No ordering guarantee
- Messages may be processed out of order

**FIFO Queue** (coming soon):
- Messages in same `MessageGroupId` process in order
- Single consumer per group (limits parallelism)

```yaml
# Future feature
queues:
  process-orders:
    fifo: true
    content_based_deduplication: true
```

## Error Handling

### Transient Errors (Retry)

Temporary failures should retry:

```go
func processOrder(ctx context.Context, order ProcessOrder) error {
    // Network timeout → retry
    payment, err := paymentService.Charge(ctx, order)
    if err != nil {
        return fmt.Errorf("payment failed: %w", err)  // Retry
    }

    // Rate limit → retry
    if payment.StatusCode == 429 {
        return errors.New("rate limited")  // Retry
    }

    return nil
}
```

### Permanent Errors (DLQ)

Non-retryable failures after max retries → DLQ:

```go
func processOrder(ctx context.Context, order ProcessOrder) error {
    // Validation error → will retry until maxReceiveCount → DLQ
    if order.Total < 0 {
        return errors.New("invalid total")  // Permanent error
    }

    // User not found → will retry → DLQ
    user, err := db.GetUser(ctx, order.UserID)
    if err == sql.ErrNoRows {
        return errors.New("user not found")  // Permanent error
    }

    return nil
}
```

## Performance

### Throughput

**Single queue handler:**
- Batch size: 10 messages
- Max concurrency: 10 Lambda instances
- Throughput: ~100 messages/second

**To scale:**

1. **Increase concurrency:**
```yaml
queues:
  process-orders:
    max_concurrency: 100  # 1,000 msg/s
```

2. **Optimize handler:**
```go
// ✅ Use connection pooling
var db *sql.DB

func init() {
    db, _ = sql.Open("postgres", os.Getenv("DATABASE_URL"))
    db.SetMaxOpenConns(10)
}

// ✅ Batch external calls
func processOrders(ctx context.Context, msgs []ProcessOrder) error {
    // Collect all order IDs
    orderIDs := make([]string, len(msgs))
    for i, msg := range msgs {
        orderIDs[i] = msg.OrderID
    }

    // Single database query
    orders, _ := db.GetOrdersByIDs(ctx, orderIDs)

    // Process batch...
}
```

3. **Use parallel processing:**
```go
func processOrders(ctx context.Context, msgs []ProcessOrder) error {
    // Process all messages in parallel
    return processInParallel(ctx, msgs, func(ctx context.Context, msg ProcessOrder) error {
        return process(ctx, msg)
    })
}
```

### Latency

**End-to-end latency:**
- Enqueue → SQS: ~10ms
- SQS → Lambda poll: 0-20s (configurable)
- Lambda cold start: 100-1000ms (first invocation)
- Lambda warm: 1-10ms overhead
- Handler execution: (your code)

**Reduce latency:**

1. **Decrease batching window:**
```yaml
queues:
  urgent-orders:
    batching_window: 0  # Invoke immediately
```

2. **Use provisioned concurrency:**
```yaml
deploy:
  queues:
    urgent-orders:
      provisioned_concurrency: 5  # Always warm
```

## Cost Optimization

### Pricing Model

- **SQS requests:** $0.40 per 1M requests (first 1M free)
- **Lambda invocations:** $0.20 per 1M invocations
- **Lambda duration:** $0.0000166667 per GB-second (ARM64)

### Cost Examples

**Scenario: 1M messages/month, batch_size=10**
- SQS requests: 1M enqueue + 100K receive = **$0.44**
- Lambda invocations: 100K = **$0.02**
- Lambda duration (100ms, 512MB): 51.2K GB-s = **$0.85**
- **Total: ~$1.31/month**

**Scenario: 10M messages/month, batch_size=10**
- SQS requests: 10M enqueue + 1M receive = **$4.40**
- Lambda invocations: 1M = **$0.20**
- Lambda duration (100ms, 512MB): 512K GB-s = **$8.53**
- **Total: ~$13.13/month**

### Optimization Tips

1. **Increase batch size** - Fewer Lambda invocations:
```yaml
queues:
  process-orders:
    batch_size: 10  # Max for SQS
```

2. **Use ARM64** - 20% cheaper compute:
```yaml

  arch: arm64
```

3. **Right-size memory** - Balance speed vs cost:
```yaml
deploy:
  queues:
    process-orders:
      memory: 512  # Start here, tune based on metrics
```

4. **Batch external calls** - Reduce handler duration
5. **Set appropriate timeouts** - Don't pay for hung handlers

## Troubleshooting

### Issue: Messages not being processed

**Check:**

1. Event source mapping is enabled:
```bash
aws lambda list-event-source-mappings \
    --function-name myapp-process-orders
```

2. Lambda has SQS permissions:
```bash
aws iam get-role-policy \
    --role-name myapp-lambda-exec \
    --policy-name sqs-access
```

3. `TRANSIRE_HANDLER` matches queue key:
```bash
aws lambda get-function-configuration \
    --function-name myapp-process-orders \
    --query 'Environment.Variables.TRANSIRE_HANDLER'
# Should output: "queue:process-orders"
```

### Issue: Messages going to DLQ immediately

**Causes:**
- Type mismatch (wrong message type)
- Handler panic/crash
- Invalid JSON

**Check CloudWatch Logs:**
```bash
aws logs tail /aws/lambda/myapp-process-orders --follow
```

**Look for:**
- `type mismatch: expected ProcessOrder, got XYZ`
- `json: cannot unmarshal...`
- `panic: runtime error...`

### Issue: Slow processing

**Check:**
1. **Lambda cold starts** - Provision concurrency
2. **Database connections** - Use connection pooling
3. **External API calls** - Add timeouts, batch calls
4. **Large messages** - Consider S3 pointer pattern

**CloudWatch Insights query:**
```
fields @timestamp, @duration, @message
| filter @type = "REPORT"
| stats avg(@duration), max(@duration), count(*) by bin(5m)
```
